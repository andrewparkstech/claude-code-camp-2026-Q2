# The Struct Skeleton (Python port)

Python port of `week1_baseline/ruby/01_struct_skeleton`. Same behavior, same
output shape (aside from the display divergences noted below) — builds on
the `Config`/`Player` code ported in `python/00_config`, adding the data
structures we constantly pass around:
- `Tool`
- `Message`
- `Context`

Ruby represents these as Structs because they're lightweight and readable for
learning; in practice we'd probably use full classes. Python has no direct
Struct equivalent, so this port uses `@dataclass` for `Tool` and `Message`
(mutable, minimal boilerplate — the closest match to a Ruby Struct) and a
plain class for `Context`, which was already a full class in Ruby.

## Setup

```bash
cd week1_baseline/python/01_struct_skeleton
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Data Structures

### Tool
| Field | Description |
|---|---|
| `name` | The name of the tool |
| `description` | Shown to the agent so it knows when to invoke the tool |
| `parameters` | The arguments that need to be passed in |
| `block` | The actual code that runs when the tool is called |

**Examples:**
```
#<Tool name=move description=Move the player in a direction (north, south, east, west, up, down) params=['direction']>
#<Tool name=attack description=Attack a target in the current room params=['target']>
#<Tool name=look description=Look around the current room params=[]>
#<Tool name=say description=Say something out loud to others in the room params=['message']>
```

### Message
A single unit of conversation between the user and the agent.

| Field | Description |
|---|---|
| `role` | Who is speaking — user, assistant, or tool_result |
| `content` | The text generated by the agent or provided by the user |
| `tool_use_id` | Links a tool result back to the specific tool call that requested it. The API requires this pairing to be exact. |

**Examples:**
```
#<Message role=user content=Explore north and tell me what you find....>
#<Message role=assistant content=Sure, let me head north and take a look....>
#<Message role=tool_result [toolu_01X] content=You move north into a torch-lit corridor....>
```

### Context
Holds everything BOUKENSHA needs to make an API call. Nothing lives outside
of this.

| Field | Description |
|---|---|
| `system` | Tells the agent what its job is. Sent as a separate field in the API call, never inside the messages array. |
| `messages` | The full conversation history, replayed on every turn |
| `tools` | The registered tools the agent is allowed to invoke |

```
#<Context task=player turns=2 tools=1>
```

## Run Example

```bash
./week1_baseline/bin/python/01_struct_skeleton
```

Expected output (values from your `.boukensha/`):

## Ruby → Python idiom differences

- `Tool#parameters.keys` prints as `[:direction]` in Ruby (the example uses
  symbol keys) vs `['direction']` in Python (string keys — the idiomatic
  dict-as-JSON-schema shape). This is a display divergence, not a bug.
- Ruby's inclusive `description[0..40]` / `content[0..60]` ranges (41/61
  characters) become Python slices `[:41]` / `[:61]`.
- `Config`'s `__str__` keeps the `Boukensha::Config` string byte-identical to
  Ruby (same choice made in the `00_config` port). `Tool`, `Message`, and
  `Context` never had a `Boukensha::` prefix in Ruby either, so their Python
  `__str__` output matches without any prefix to preserve.
- This step's `config.py` drops the `PROMPTS_DIR` module constant that
  `00_config`'s has — Ruby's `01_struct_skeleton/lib/boukensha/config.rb`
  drops it too, and nothing in this step's example depends on it (the system
  prompt is resolved but never printed).
